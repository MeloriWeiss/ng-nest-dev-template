## Архитектурный стиль (DDD)

Проект построен по принципам **Domain-Driven Design (DDD)**. Весь код разделен на изолированные бизнес-домены (например, `auth`, `users`, `profile`), которые находятся внутри `libs/web` и `libs/api`.

Внутри каждого домена кодовая база строго разносится по слоям:

| Слой | Назначение | Ограничения |
| :--- | :--- | :--- |
| **`data-access`** | Работа с данными: API-сервисы, Стор (State Management), DTO, сущности БД. | Не содержит элементов пользовательского интерфейса. |
| **`common-ui` / `ui`** | Глупые (dumb) UI-компоненты. Принимают данные через `input()`, отдают через `output()`. | Не знают про бизнес-логику и не инжектят глобальные сторы. |
| **`feature-...`** | Умные (smart) компоненты, экраны и страницы. Связывают UI со сторами. | Управляют маршрутизацией и бизнес-сценариями. |

Граф зависимостей приложения можно посмотреть с помощью команды `nx graph`.
Основные правила:
- Избегать лишней взаимосвязи библиотек
- web-shared может зависеть от web-data-access
- web-common-ui не зависит ни от того
- shared зависит от web-common-ui

web-common-ui - библиотека "глупых" ui-компонентов, использующихся во всём приложении
shared - та же web-common-ui, но с более "умными" компонентами, которые могут использовать web-data-access.

- libs/api хранит библиотеки бэкенда
- libs/web - фронтенда
- shared - общие данные (типы, DTO, валидаторы)

## Создание модулей и библиотек

Никогда не создавайте папки для новых модулей вручную. Для генерации всегда используется **Nx CLI**, что гарантирует автоматическое добавление путей в `tsconfig.base.json`.

### 1. Веб-библиотеки (Angular)

Генерируются в директорию `libs/web/<domain>/<layer>` с префиксом `sl`:

```bash
# Например, слой для домена (логического функционала) example
npx nx g @nx/angular:library --name=web-example --directory=libs/web/example
```

Библиотеку необходимо создавать для вынесения логического блока функциональности в отдельный модуль.

Рекомендуется создавать библиотеки через плагин `Nx Console` вместо использования команд.

### 2. Бэкенд-библиотеки (NestJS)

Генерируются в директорию `libs/api/<domain>/<layer>`:

```bash
# Слой логики и работы с базой данных для API billing
npx nx g @nx/nest:library --name=api-example --directory=libs/api/example
```

Unit test runner выбирать Jest.

`ВНИМАНИЕ:` после создания библиотеки необходимо привести алиас в `tsconfig.base.json`, по которому будет импортироваться
эта библиотека, к формату `@sl/<layer>/<domain>`. В пример уже существующие библиотеки.

## Фронтенд на Angular 22

Мы пишем исключительно в функциональном стиле, используя **Standalone-компоненты** и **Signals API**.

### Создание компонентов

Компоненты генерируются строго внутри интерфейсных или фиче-библиотек:

```bash
# Компонент для домена auth
npx nx g @nx/angular:component libs/web/auth/src/lib/ui/example/example
```

Компоненты необходимо создавать для вынесения логической части интерфейса.

Рекомендуется создавать компоненты через плагин `Nx Console` вместо использования команд.

### Основные правила:

- Внедрение зависимостей происходит только через функцию `inject()`, конструкторы не используются.
- Входные и выходные данные объявляются через сигнальные функции `input()` / `input.required()` и `output()`.

Пример базового компонента:

```typescript
import { Component, inject, input, output } from '@angular/core';
import { CommonModule } from '@angular/common';
import { BillingService } from '@sl/web/billing/data-access';

@Component({
  selector: 'wm-billing-card',
  standalone: true,
  imports: [CommonModule],
  templateUrl: './billing-card.component.html',
  styleUrls: ['./billing-card.component.scss'],
})
export class BillingCardComponent {
  // Внедрение зависимостей через inject()
  #billingService = inject(BillingService);

  // Signals Inputs & Outputs
  userId = input.required<string>();
  cardClicked = output<void>();
}
```

Приватные переменные объявляются нативно при помощи символа решётки `#`, ключевое слово `private` не используется.

## Управление состоянием (Signals Store)

В проекте не используются тяжелые стейт-менеджеры вроде NgRx (Redux-подход). Состояние организуется с помощью встроенных **Angular Signals** и RxJS для асинхронных запросов. Файлы сторов всегда лежат в слое `data-access`.

### Шаблон реализации стора (`*.store.ts`)

Сторы пока не создаём.

## Бэкенд на NestJS

Бэкенд-код организуется внутри приложений `apps/api` (эндпоинты, глобальные перехватчики) и модулей в `libs/api`. Для взаимодействия с базой данных PostgreSQL используется **Prisma ORM**.

- **Контроллеры и Эндпоинты:** Находятся в приложениях или фиче-библиотеках бэкенда.
- **Сервисы и Репозитории:** Инкапсулируют логику работы с Prisma и внешними S3-хранилищами (MinIO).

## Правила импортов

1. **Запрещены относительные пути между библиотеками.** Написание путей вида `import { ... } from '../../../../auth/src'` заблокирует сборку.
2. **Только tsconfig-алиасы.** Используйте абсолютные пути воркспейса: `import { AuthService } from '@sl/web/auth/data-access';`.
3. Любая сущность, которая используется за пределами своей библиотеки, должна быть экспортирована в её корневом файле `index.ts` (Public API библиотеки).
